# train-oomawari

JR東日本の東京近郊区間を対象として、指定した2駅間の大回り乗車候補経路を探索するプロジェクトです。

> 重要: グラフ上の最長経路と、実際にJR東日本の営業規則上乗車できる経路は同義ではありません。制度上の可否を最終判断する際は、必ずJR東日本の現行規則・公式案内を確認してください。

## 1. 目的

2駅を指定し、リポジトリに保存された鉄道網データをグラフとして扱って、現在の探索モデルで営業キロの合計が最大になる単純経路を求めます。

利用方法は次の2つです。
- GitHub Actions: 開発者・管理者向け。workflow_dispatchで実行し、結果をArtifactとして保存。
- GitHub Pages: 一般利用者向け。駅名を検索してブラウザから実行。MILPも利用者のブラウザ内で実行。

## 2. ディレクトリ構成

    oomawari.py                    # 探索本体
    test_oomawari.py               # 単体テスト
    data/tokyo_near_zone.csv       # 固定鉄道網データ
    docs/index.html                # GitHub Pages用Web UI
    scripts/build_site.py          # Pages公開用ファイル生成
    .github/workflows/omawari.yml  # Actions経路探索
    .github/workflows/pages.yml    # GitHub Pagesデプロイ
    .github/workflows/test.yml     # 単体テスト
    .github/workflows/bootstrap-data.yml # データ初期取得・更新用

`site/` は `build_site.py` が生成する公開用ディレクトリです。

## 3. データ

`data/tokyo_near_zone.csv` は鉄道網を表す固定入力データです。通常の経路探索実行時には外部APIへアクセスしません。

データ更新時には、駅名、路線、区間、営業キロ、同名駅、東京近郊区間の範囲を確認してください。このCSVは鉄道網データであり、JR東日本の営業規則そのものではありません。

## 4. 探索アルゴリズム

`oomawari.py` はSciPyの `milp` とHiGHSを利用した混合整数線形計画法（MILP）で探索します。

概念モデル:
- 駅 = 頂点
- 鉄道区間 = 無向辺
- 区間の方向 = 有向選択変数
- 駅を経路に含めるか = 0/1変数
- 目的関数 = 選択区間の営業キロ総和を最大化
- 始点・終点 = 1本の経路端点
- 中間駅 = 1本入って1本出る
- 同一駅を2回使用しない
- commodity flowで選択された経路の連結性を保証

MILPがoptimalを返した場合の値は、「現在のCSVと現在のMILPモデル」に対する最大値です。JR東日本の規則を完全に形式化した最大値を意味しません。

制約を変更するときは、同一駅・同一区間の再利用、不連結な閉路、経路復元が正しいことをテストしてください。

## 5. GitHub Actions版

`omawari.yml` を Actions から手動実行します。

GitHubの Actions → Omawari route → Run workflow から出発駅・到着駅を選択します。駅数が多いため、選択肢は日本語の五十音順で管理します。

結果は `omawari-result` Artifact に保存されます。Actions版は開発時の動作確認、大きな計算、結果保存、Web版との比較に使用します。

## 6. GitHub Pages版

Web UIは `docs/index.html` です。Pagesのビルド時に `scripts/build_site.py` が駅データを生成します。

処理の流れ:

    data/tokyo_near_zone.csv
             ↓
    build_site.py
             ↓
    stations.json / data.csv / oomawari.py
             ↓
    ブラウザ
             ↓
    Pyodide + SciPy / HiGHS
             ↓
    最大経路

GitHub Pagesはサーバー側Pythonを実行しないため、Python探索処理をPyodide上でブラウザ実行しています。

これにより計算サーバーを共有せず、多数の利用者が各自の端末で計算できます。一方、MILPはCPU負荷が高いため、スマートフォン等では時間がかかる可能性があります。

## 7. 駅検索UI

Web版は704件程度の巨大なHTMLプルダウンではなく、駅名を入力して候補を絞り込む方式です。

検索対象は駅名とひらがな読みです。例: 「東京」でも「とうきょう」でも検索できます。候補は読み仮名順です。

駅名をUIへ直接ハードコードせず、

    CSV → build_site.py → stations.json → Web UI

のデータフローを維持してください。読み仮名生成には `pykakasi` を使用します。

## 8. テスト

ローカルでは次を実行します。

    python3 -m pip install scipy
    python3 -m unittest -v

GitHub Actionsでは `test.yml` がテストします。

アルゴリズム変更時は、始点・終点、単純経路、分岐、閉路、区間長、経路復元をテスト対象にしてください。

## 9. JR東日本の制度との分離

このプロジェクトでは「鉄道網の計算」と「営業規則上の乗車可否」を分離します。

    鉄道網: CSV → グラフ → MILP → 最大営業キロ
    制度:   JR東日本の現行規則 → 適用条件 → 乗車可否

駅の重複禁止だけでは表現できない営業規則上の条件を追加する場合は、どの公式規則のどの条件を、数理モデルのどの制約に対応させたかをコードコメントとREADMEに記録してください。

## 10. データ更新手順

1. `data/tokyo_near_zone.csv` を更新する。
2. 駅数・区間数・同名駅を確認する。
3. 営業キロを確認する。
4. `python3 -m unittest -v` を実行する。
5. Actionsのテストを確認する。
6. Actions版で代表的な駅間を計算する。
7. Pages版でも同じ入力を計算する。
8. 両者の結果を比較する。
9. READMEまたはコミットメッセージに更新日・変更理由を残す。

## 11. 既知の制約と改善候補

### 駅ID

現在は駅名を頂点識別に利用しています。同名駅や路線固有の駅を安全に扱うため、将来的には `station_id`、`station_name`、`line_id` を分離することを推奨します。

### 規則の完全形式化

将来的に制度を厳密に形式化する場合は、東京近郊区間の対象範囲、経路選択条件、同一駅再通過条件、区間・分岐ごとの特例、営業キロ・運賃計算を個別にモデル化してください。

### Web性能

Pyodide + SciPyをブラウザで実行するため、端末性能によって速度が変わります。必要に応じてWeb Worker、事前計算、駅ペア結果キャッシュ、サーバー側MILP、WASM最適化などを検討できます。

## 12. 開発原則

1. 鉄道データと営業規則を混同しない。
2. 経路計算の実行時依存を外部APIにしない。
3. 同じコミット・同じ入力なら再現可能な状態を維持する。
4. MILPの制約を変更したらテストを追加する。
5. Actions版とWeb版で探索モデルを分岐させない。
6. 将来的には安定した駅IDを導入する。
7. JR東日本の制度変更は公式情報を確認してから反映する。
8. UI、データ、探索ロジックを分離する。

## 13. 代表的な確認ケース

現在の代表ケースは `東京 → 新宿` です。Actions版とWeb版の結果比較に使用します。

ただし、その結果をJR東日本が制度上認める経路の最終確定値として扱わないでください。

## 14. 変更時に残す情報

次の変更では、コミットメッセージまたはREADMEに理由を残してください。

- `data/tokyo_near_zone.csv` の更新
- MILP制約の変更
- 駅名正規化の変更
- 駅ID方式の変更
- JR東日本の制度解釈の変更
- Web版の計算方式の変更
- Pages公開方式の変更

特に「なぜその制約を追加したのか」を残してください。最適化上の都合なのか、営業規則上の理由なのかを後から判別できることが重要です。
